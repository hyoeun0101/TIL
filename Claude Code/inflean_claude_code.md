
## 09_rewind

### /rewind
- 대화 상태를 이전 메시지로 되돌립니다.
- 다음과 같이 생각하세요: 
  - `git reset --hard`
  - 또는 이전 컨텍스트 스냅샷을 복원하는 것.
- 선택한 메시지 이후에 발생한 모든 것을 제거하고 세션을 해당 시점으로 복원합니다.

### `/rewind`가 중요한 이유
- Claude Code에서 컨텍스트 = 메모리 + 지시사항 + 파일 + 대화 기록입니다.
- 다음과 같은 상황이라면:
  - 잘못된 지시를 내렸거나 
  - 에이전트가 잘못된 방향으로 진행하거나 
  - 너무 많은 노이즈로 컨텍스트를 오염시켰거나 
  - 대화를 다르게 분기하고 싶다면 
  - 처음부터 다시 시작할 필요가 없습니다. 
  - 그냥 이렇게 하면 됩니다:
  - `/rewind`
  - 그리고 돌아갈 메시지를 선택하세요.

### 내부적으로 실제로 일어나는 일
- `/rewind`를 사용하면:
  - Claude가 선택한 지점 이후의 메시지를 삭제합니다 
  - 토큰 사용량이 감소합니다 
  - 컨텍스트 창이 확보됩니다 
  - 이후 응답은 해당 상태에서 다시 생성됩니다
- 이는 다음에 중요합니다:
  - 토큰 예산 관리 
  - 긴 디버깅 세션 
  - 에이전트 실험

### `/rewind`를 사용해야 할 때

- ✅ 좋은 사용 사례:
  - 잘못된 시스템 지시를 내렸을 때 
  - 에이전트가 목표를 잘못 이해했을 때 
  - 관련 없는 컨텍스트를 실수로 노출시켰을 때 
  - 대안적인 프롬프트 경로를 테스트하고 싶을 때

  - ❌ 사용하지 말아야 할 때:
  - 사소한 수정 → 그냥 명확히 설명하세요 
  - 작은 개선 → 초기화할 필요 없습니다 
  - 두 출력을 비교해야 할 때 (수동으로 복사하고 분기하는 것이 더 좋습니다)

### 실용적인 워크플로 예시

- 나쁜 워크플로
  - 프롬프트 → 잘못된 방향 → 더 많은 프롬프트 → 더 많은 혼란 → 새 터미널 시작 → 컨텍스트 손실

- 더 나은 워크플로:
  - 프롬프트 → 잘못된 방향 → `/rewind` → 프롬프트 재작성 → 깔끔하게 계속 진행

### 🔥 최종 요점

- Claude Code는 단순한 prompting이 아닙니다.
- AI 시스템을 위한 상태 관리입니다.
- 그리고 `/rewind`는 여러분의 롤백 메커니즘입니다.

## 10_output_style

### `/output-style`

- `/output-style`은 Claude Code의 시스템 프롬프트를 변경합니다.
  - 즉:
  - 단순히 포맷을 변경하는 것이 아닙니다 
  - Claude의 동작 방식을 변경합니다 
  - 기본 시스템 지시사항을 대체합니다 
  - 이것은 표면적인 옵션이 아닌, 근본적인 동작 전환입니다.

### output-style이 중요한 이유

- Claude Code는 일반적으로 다음에 최적화된 시스템 프롬프트로 동작합니다:
  - 소프트웨어 엔지니어링 작업 
  - 효율적인 코드 수정 
  - 불필요한 설명 최소화
- 출력 스타일을 변경하면:
  - 기본 지시사항 세트를 대체합니다 
  - Claude의 커뮤니케이션 패턴을 변경합니다 
  - 설명의 양을 바꿉니다 
  - 상호작용 흐름을 잠재적으로 변경합니다

- 이는 다음 목적에 중요합니다:
  - 교육 
  - 페어 프로그래밍 
  - 지식 전달 
  - 팀 온보딩 
  - 대화형 멘토링

### 기본 제공 출력 스타일
- Default (기본)
  - 목적: 최적화된 소프트웨어 엔지니어링 실행. 
  - 특징:
    - 작업 완료에 집중 
    - 효율적인 응답 
    - 최소한의 추가 설명 
    - 실제 코딩 생산성을 위해 설계됨 
  - 대부분의 엔지니어가 매일 사용하는 스타일입니다.

- Explanatory (설명형)
  - 목적: 교육적 컨텍스트 추가.
  - 특징:
    - 추론 과정 설명 
    - 결정에 대한 통찰 제공 
    - 기본보다 더 상세함
    - "왜"를 이해하는 데 유용 
  - 최적 용도:
    - 내부 교육 
    - 아키텍처 설명 
    - 주니어 엔지니어 멘토링 
    - 기술적 심층 분석

- Learning (학습형)
  - 목적: 대화형 학습 모드.
  - 특징:
    - 단계별 안내
    - `TODO(human)` 같은 마커 삽입 가능
    - 스스로 일부를 완성하도록 유도
      - 페어 프로그래밍 시뮬레이션
  - 최적 용도:
    - 교육 환경 
    - 워크숍
    - 실습 코딩 세션
    - 부트캠프 방식의 교육

### 내부적으로 실제로 일어나는 일

- 출력 스타일은 기본 시스템 프롬프트를 대체합니다
- 기본 간결 모드 지시사항을 제외합니다 
- 커스텀 스타일은 명시적으로 포함하지 않는 한 코딩 지시사항을 생략할 수 있습니다 
- 스타일의 내용이 활성 시스템 프롬프트가 됩니다 
- 이것이 강력한 이유:
  - Claude가 자신의 역할에 대해 생각하는 방식을 재정의하는 것입니다.

### custom output style

- 사용자 레벨: `~/.claude/output-styles/<FILE.MD>` 생성
- 프로젝트 레벨: `.claude/output-styles/<FILE.MD>` 생성


## 12_bash_command

### ⚡ Claude Code의 `!` Bash 명령어

- Claude Code에서 `!`를 앞에 붙이면: `!<bash command>`
- "이것을 즉시 실제 bash 명령어로 실행해."라는 의미입니다.
- 👉 AI 해석을 우회하고 쉘에서 직접 실행합니다.


### `!`를 사용해야 할 때
- 빠른 확인: `!pwd`
- Git 작업: `!git status`
- 환경 디버깅: `!env`
- 알려진 명령어 재실행: `!npm run dev`

###  `!<bash command>` — 숨겨진 슈퍼파워

- 처음 보기에: `!ls`는 "그냥 터미널 명령어 실행"처럼 보입니다.
- 하지만 Claude Code 내부에서는 실제로 의미하는 것은 "명령어를 실행하고 출력을 Claude의 컨텍스트로 다시 피드백해."

- 🧑‍💻 일반 터미널: 직접 읽고 → 해석하고 → 다음 단계 결정
- 🤖 Claude Code의 `!`: 출력이 여러분에게도 보이고 Claude의 컨텍스트에도 입력됨

### 이것이 강력한 이유

- 자동 디버깅 - `!npm run build`
  - 의존성 누락으로 빌드 실패 ->  `npm install` 실행하지 않고, 실패 원인 파악을 하고 다음 실행을 추천해줌.

- 다단계 추론 - `!ps aux | grep python`
  - 프로세스 파싱 → 비정상적인 것 식별 → 수정 제안

- 반복적 수정 루프 - `!run command`
  - 오류 → Claude가 출력 읽음 → 수정 제안

- 컨텍스트 인식 자동화 - `!kubectl describe pod my-app`
  - 이벤트/로그 읽기 → 충돌 원인 진단 → 설정 변경 제안

## 13_debugging

### 🐛 Claude Code 디버깅 옵션

- 훅을 설정했는데 왜 실행이 안 되지?
- MCP 서버가 연결이 안 돼 — 어디를 확인해야 하나?
- API 호출이 느린데, 병목이 어디지?
  - → 이것이 바로 디버깅 옵션이 필요한 이유입니다.

### 디버깅 옵션이 중요한 이유

- Claude Code는 내부에서 많은 작업을 수행합니다.
- API 호출, MCP 통신, Hooks 실행, 파일 I/O — 모두 병렬로 진행됩니다.
- 기본 모드에서는 이 모든 것이 블랙박스 안에 숨겨져 있습니다.
- 무언가 잘못되면, 디버그 플래그가 "어디서 막혔는지" 확인하는 데 필수적입니다.
- Plugins, Hooks, 또는 MCP 서버를 개발한다면 거의 매일 사용하게 될 것입니다.

### 디버깅 옵션

- `--verbose`
  - 모든 턴별 출력을 원할 때 사용
  - `claude --verbose -p --output-format stream-json "Why is the sky blue?"`

- `--debug [filter]`
  - 카테고리별로 내부 동작(API/Hooks/MCP) 추적
  - `claude --debug "api,hooks,mcp"`
  - `claude --debug "!statsig,!file"`

- `--debug-file <path>`
  - 디버그 로그를 파일에 저장 (자동으로 `--debug` 활성화)
  - `claude --debug-file ./claude.log`


## 17_hooks

### `/hooks`
- `/hooks`를 사용하면 Claude Code 내부의 특정 라이프사이클 이벤트에서 실행되는 자동화 액션을 정의할 수 있습니다.
- 다음과 같이 생각하세요:
  - Git hooks (pre-commit, post-commit)
  - CI/CD 파이프라인 트리거 
  - AI 실행을 위한 미들웨어 
  - 이를 통해 정해진 단계에서 Claude의 동작을 가로채거나 보강할 수 있습니다.

### 중요한 이유

- 팀이나 조직에서 `/hooks`는 다음을 가능하게 합니다:
    - ✅ 정책 시행 
    - ✅ 보안 스캔 
    - ✅ 로깅 및 관찰 가능성 
    - ✅ 컨텍스트 주입 
    - ✅ 컴플라이언스 검사 
    - ✅ 자동 포맷팅 / 린팅 
    - ✅ 실행 전 가드레일 
- AI 실행 라이프사이클에 대한 프로그래밍 가능한 제어.

### Hook 라이프사이클
-  `SessionStart`: 세션이 시작되거나 재개될 때
- `UserPromptSubmit`: 프롬프트를 제출할 때, Claude가 처리하기 전 (정책 시행)
- `PreToolUse`: 도구 호출이 실행되기 전. 차단 가능
- `PermissionRequest`: 권한 대화상자가 나타날 때
- `PostToolUse`: 도구 호출이 성공한 후 (로깅 및 검증)
- `PostToolUseFailure`: 도구 호출이 실패한 후
- `Notification`: Claude Code가 알림을 보낼 때
- `SubagentStart`: 서브에이전트가 생성될 때
- `SubagentStop`: 서브에이전트가 완료될 때
- `Stop`: Claude가 응답을 마칠 때
- `TeammateIdle`: 에이전트 팀 동료가 유휴 상태가 되려 할 때
- `TaskCompleted`: 작업이 완료로 표시될 때
- `ConfigChange`: 세션 중 설정 파일이 변경될 때
- `WorktreeCreate`: `--worktree` 또는 `isolation: "worktree"`를 통해 워크트리가 생성될 때. 기본 git 동작을 대체
- `WorktreeRemove`: 세션 종료 시 또는 서브에이전트가 완료될 때 워크트리가 제거될 때
- `PreCompact`: 컨텍스트 압축 전
- `SessionEnd`: 세션이 종료될 때

예시: `~/.claude/settings.json`에 hooks 설정하기.

## 18_permissions

### 왜 권한 시스템이 필요한가?

- 실수 방지
    - `rm -rf /`와 같은 위험한 명령어나 `.env`와 같은 파일 접근에 대한 안전망.

- 주도권 유지
  - 모든 파일 변경, 쉘 명령어, 네트워크 요청에 대해 최종 결정권을 가집니다.

- 가시성
  - 승인 프롬프트가 Claude가 무엇을 하려는지 한 번에 하나씩 정확히 보여줍니다. 
- Claude Code 사용자의 약 93%가 권한 프롬프트를 승인합니다.

### `/permissions` 살펴보기

- Claude Code 세션 내에서 `/permissions`를 입력하면 권한 관리 UI가 열립니다.
- 모든 권한 규칙과 각 규칙이 어느 `settings.json` 파일에서 왔는지 목록을 보여줍니다.

- 세 가지 규칙 유형:
  - `allow`: 수동 승인 없이 Claude가 도구를 사용하도록 허용합니다.
  - `ask`: 도구가 사용될 때마다 확인을 요청합니다.
  - `deny`: Claude가 도구를 아예 사용하지 못하도록 막습니다.

### 규칙 평가 방식

- Claude가 도구(Bash, Edit, WebFetch 등)를 사용하려 할 때마다 다음 순서로 규칙이 확인됩니다:
  - Deny → Ask → Allow → Default

권한 계층: 세 가지 도구 유형 (승인 여부)
읽기 전용 (없음): `ls`, `cat`, `grep` 또는 파일 읽기
Bash 명령어 (있음 - 프로젝트별 영구): 쉘 실행
파일 수정 (있음 - 세션 종료 시까지): 파일 편집/쓰기

**규칙 문법: `Tool(specifier)`**

`Bash`: 모든 Bash 명령어에 매칭
`Bash(npm run build)`: 해당 정확한 명령어에만 매칭
`Bash(npm run *)`: `npm run`으로 시작하는 명령어에 매칭
`Read(./.env)`: 현재 디렉토리의 `.env` 파일 읽기
`Edit(/src/**/*.ts)`: 프로젝트 `src/` 하위의 모든 TS 파일 편집
`WebFetch(domain:example.com)`: example.com으로의 fetch 요청

와일드카드 팁:
`Bash(ls *)` vs. `Bash(ls*)`
경로 앵커: `//path` 절대경로, `~/path` 홈, `/path` 프로젝트 루트, `path` 현재 디렉토리

**알아두면 좋은 동작들**

복합 명령어: Claude Code는 쉘 연산자(`&&`, `||`, `;`, `|`)를 인식합니다. `Bash(safe-cmd *)`가 있더라도 `safe-cmd && other-cmd`는 모든 서브 명령어가 매칭될 때만 허용됩니다.

읽기 전용 명령어 자동 허용: `ls`, `cat`, `pwd`, `grep`, `find`, `diff`는 프롬프트 없이 허용됩니다.

프로세스 래퍼 제거: `timeout`, `time`, `nice`, `nohup` 같은 래퍼는 매칭 전에 제거됩니다. 따라서 `Bash(npm test *)`는 `timeout 30 npm test`도 포함합니다.

일부를 제외한 모든 Bash를 허용하려면: `allow`에 `"Bash"`를 넣고, `PreToolUse` hook으로 특정 명령어를 거부하세요. 가장 신뢰할 수 있는 방법입니다.

**권한 모드**

`default`: 표준 동작. 각 도구를 처음 사용할 때 프롬프트를 표시합니다.
`acceptEdits`: 작업 디렉토리 내 파일 편집과 일반 파일시스템 명령어(`mkdir`, `touch`, `mv`, `cp`)를 자동으로 수락합니다.
`plan`: 플랜 모드. 파일을 읽고 읽기 전용 명령어를 실행해 탐색하지만 소스 파일을 편집하지 않습니다.
`auto`: 백그라운드 안전 검사와 함께 도구 호출을 자동 승인합니다. 모델 기반 분류기가 요청과의 일치 여부를 검증합니다.
`dontAsk`: `/permissions` 또는 allow 규칙으로 사전 승인된 경우를 제외하고 도구를 자동으로 거부합니다.
`bypassPermissions`: 모든 프롬프트를 건너뜁니다. (`rm -rf /`는 여전히 서킷 브레이커로 프롬프트를 표시합니다.)

**실제 적용 및 공유**

설정 우선순위 (높을수록 강함):
관리형 설정: CLI 인수를 포함한 어떤 것으로도 재정의 불가
커맨드 라인 인수: 임시 세션 재정의 (`claude --permission-mode bypassPermissions`)
로컬 프로젝트 설정: `.claude/settings.local.json`
공유 프로젝트 설정: `.claude/settings.json` (팀용, git에 커밋)
사용자 설정: `~/.claude/settings.json`

팀과 공유하기:
`/permissions`에서 규칙을 추가한 후 결과를 `.claude/settings.json`에 저장하고 git에 커밋하세요.

## 19_claude_memory.pdf

**🧠 Claude Code에서 "메모리"의 의미**

Claude Code에서 메모리란 세션 간에 저장되는 영속적 컨텍스트를 의미합니다.
세션 컨텍스트: 임시 대화 기록, 현재 세션에만 유효
메모리: 영속적으로 저장되는 정보, 세션 간 유지

따라서 메모리는 단순한 토큰 기록이 아닙니다.
Claude가 기억할 수 있는 구조화된 정보입니다:
여러분의 역할
프로젝트 세부 정보
코딩 선호도
반복적인 워크플로
커스텀 시스템 지시사항

**메모리가 중요한 이유**

메모리 없이:
새 세션마다 백지에서 시작합니다.
환경을 다시 설명해야 합니다.

메모리 있으면:
Claude가 여러분에게 적응합니다.
컨텍스트를 반복하지 않아도 됩니다.
개인 AI 팀원에 더 가까워집니다.

예를 들어, 다음과 자주 작업한다면:
AWS EKS, Terraform IAM 정책, Kubernetes 위의 Spark, 스태프 레벨 아키텍처 논의
Claude는 이를 기억하고 그에 맞게 응답할 수 있습니다.

**`/memory` 명령어**

`/memory` 명령어는 영속적으로 저장된 정보를 관리하는 데 사용됩니다.
다음과 같이 생각하세요: 여러분과 여러분의 환경에 대한 구조화된 지식 베이스.

**메모리에 저장해야 할 것**

전문 워크플로에서 좋은 후보:
✅ 안정적인 정보: 역할, 기술 스택, 코딩 스타일, 프로젝트 명명 규칙, 회사 제약사항
❌ 좋지 않은 후보: 임시 디버깅 상태, 일회성 질문, 민감한 비밀 (키, 패스워드)

**`/memory` vs `/context`**

`/context`: 토큰 사용량 표시, 대화 기록 표시 → RAM과 같음
`/memory`: 세션 간 유지, 편집 가능 → SSD와 같음

**내부 동작 (개념적으로)**

메모리는:
세션 토큰과 별도로 저장됩니다
시스템 프롬프트에 자동으로 주입됩니다
응답을 형성하는 데 사용됩니다
다음의 구조화된 확장처럼 동작합니다: 시스템 프롬프트 + 커스텀 지시사항
따라서 메모리는 다음에 영향을 미칩니다:
톤, 기술적 깊이, 가정, 아키텍처 논의

**엔지니어를 위한 고급 사용 사례**

예를 들어 다음을 저장할 수 있습니다:
Python을 선호합니다.
명확한 input/output 분리가 있는 Terraform 모듈을 선호합니다.
AWS 모범 사례를 따릅니다.

**일반적인 오해**

❌ 메모리 = 채팅 기록
❌ 메모리 = 토큰 버퍼
❌ 메모리 = 로컬 파일 캐시
✅ 메모리 = 영속적인 구조화 컨텍스트

## 20_claude_skills_command
### 🎯 Skills란 무엇인가?

- Skills는 Claude Code 내에서 Claude의 능력을 확장하는 모듈식 지시사항입니다.
- 규칙, 구조, 반복 가능한 로직으로 Claude에게 특정 작업 수행 방법을 가르칩니다 
  - Claude가 자동으로 또는 명령에 따라 로드할 수 있는 "플러그인" 또는 도메인 특화 전문가 모듈과 같습니다.
- Skill을 다음과 같이 생각하세요: 이런 요청이 들어오면 Claude가 따르는 미리 정의된 Workflow.

### 🤖 Skills가 중요한 이유

- Skills는 다음 방식으로 Claude를 향상시킵니다:
  - 작업 특화 허용: Claude가 새로운 작업을 매번 추측하지 않습니다.
  - 컨텍스트 오버헤드 감소: 관련 지시사항만 로드하여 컨텍스트 노이즈를 제한합니다. 
  - 조직 지식 capture: 회사 스타일 가이드, 워크플로, 템플릿등을 미리 정의.
  - 반복 가능한 워크플로 자동화: 엄격한 구조의 작업을 코드화할 수 있습니다. merge하고, deploy까지 자동화 가능.
- Skills는 무작위 프롬프트가 아니라 Claude가 지능적으로 로드할 수 있는 작고 구조화된 재사용 가능한 지시사항입니다.

### 🧠 Skills의 작동 방식
- 감지 및 로딩
- Claude가 프롬프트를 받으면:
  - 사용 가능한 Skills의 설명을 검토합니다. 
  - 어떤 것이 관련 있는지 결정합니다. 
  - 필요할 때만 동적으로 지시사항을 로드합니다.
- 이렇게 하면 컨텍스트 창이 넘치는 것을 방지합니다.

- 호출 방식
  - Skills는 두 가지 방식으로 사용할 수 있습니다:
  - 📌 자동 호출: Claude가 대화 중 관련 Skill을 로드하기로 결정합니다. 예를 들어, 문서 포맷 Skill이 요청과 관련 있으면 Claude가 명시적으로 이름을 지정하지 않아도 적용할 수 있습니다.
  - 📌 수동 호출: 사용자가 슬래시 명령어로 Skill을 트리거합니다: `/skill-name`. Claude가 해당 Skill의 지시사항을 실행합니다.

### Claude Code Skill의 구조

- `SKILL.md`에 포함되는 것:
  - YAML Frontmatter: 다음과 같은 메타데이터 정의:
  - `name`: 명령어 이름, `description`: 사용 시기와 방법, 호출 방식 제어 (수동 vs 자동), 허용 도구 
- 마크다운 지시사항: Skill이 호출될 때 Claude가 따르는 직접 작성된 로직.

### 🧩 Skill 콘텐츠 유형

- Skills는 폴더 내에 여러 종류의 콘텐츠를 포함할 수 있습니다:
  - `SKILL.md`: Claude가 사용하는 메인 지시사항
  - 지원 파일: 필요할 때만 로드되는 템플릿 또는 API
  - 스크립트: 실행 가능한 헬퍼 (예: shell/Python)
  - 예시/참조 문서: 예상 출력 명확화
- Claude는 핵심이 아닌 파일을 필요할 때만 로드하여 컨텍스트 공간을 보존합니다.

### 🔧 제어 및 유연성

- Skills는 Claude가 언제 어떻게 사용할지 설정할 수 있는 frontmatter 옵션을 지원합니다:
  - ✨ 자동 vs 수동: `disable-model-invocation: true`
  - ✨ 사용자 전용 또는 내부 사용: `user-invocable: false`
  - ✨ 도구 제한: `allowed-tools: Read, Grep`
- 이 제어를 통해 워크플로 자동화를 관리할 수 있습니다 (예: 배포 Skills는 자동으로 실행되어서는 안 됩니다).

**🧠 Skill 활성화 흐름**

- 예를 들어 `/deploy production`을 입력하면:
  - a. Claude가 `/deploy`를 Skill의 이름으로 인식합니다. 
  - b. Skill의 지시사항을 로드합니다 (`SKILL.md` + 선택적 파일). 
  - c. `production`을 `$ARGUMENTS`으로 받아서 스크립트에 셋팅.
  - d. 로직을 단계별로 실행합니다.
- 이렇게 하면 워크플로가 예측 가능하고 재사용 가능해집니다.

### ✅ 모범 사례
- Claude가 Skills를 쿼리에 매칭할 수 있도록 명확한 설명을 제공하세요. 
- 임시 프롬프트가 아닌 반복 가능하고 구조화된 작업에 Skills를 사용하세요. 
- 일관성을 위해 조직 전체 Skills를 중앙 디렉토리에 저장하세요.
- `SKILL.md`는 간결하게 유지하고 무거운 참조 문서는 지원 파일에 넣으세요.



- athrophic skills git repo 다운로드해서 `.claude/skills`에 넣어서 사용할 수 있음.
- ex) `/frontend-design 프롬프트`

## 23_auto_memory

### Auto Memory란?

- 수동으로 명령어를 실행하지 않아도 대화에서 유용한 정보를 자동으로 메모리 파일에 저장합니다.
- 세션 간에 중요한 컨텍스트를 Claude가 기억하도록 도와줍니다.

- `.claude/projects/<project>/memory/MEMORY.md`

### Auto Memory 작동 방식 
- 📌 메모리 로딩 규칙
  - `MEMORY.md`의 첫 200줄이 모든 대화 시작 시 로드됩니다. 
  - ⚠️ 200줄 이후의 콘텐츠는 세션 시작 시 로드되지 않습니다. 
  - 이 제한 내에 유지하기 위해 Claude는 `MEMORY.md`를 간결하게 유지하고 세부 메모를 별도 토픽 파일로 이동합니다. 
- 200줄 제한은 `MEMORY.md`에만 적용됩니다.
  - `CLAUDE.md` 파일은 길이에 상관없이 전체가 로드됩니다. 단, 짧은 `CLAUDE.md` 파일이 더 나은 준수를 만들어냅니다.

### 🔄 세션 중
- Claude는 세션 중에 메모리 파일을 읽고 쓸 수 있습니다. 
- Claude Code 인터페이스에서 다음과 같은 메시지가 보일 때:
  - "Writing memory" / "Recalled memory"
- Claude가 다음과 활발하게 상호작용하고 있는 것입니다:
  - `~/.claude/projects/<project>/memory/`

### Auto Memory가 저장하는 것

- Auto Memory는 다음을 저장합니다:
  - Long-term preferences, 영속적 지시사항, 중요한 프로젝트 컨텍스트, 재사용 가능한 제약사항

- 저장하지 않는 것:
  - 임시 세부 정보, 일회성 대화 내용, 단기 컨텍스트 
- 세션 간에 유용하다고 판단된 정보만 저장됩니다.
- 200라인만 읽기때문에 간결하게 작성하자!

에이전트는:
요청 해석, 사용할 도구 결정, 액션 실행, 결과 반환

파일 읽기, 코드 수정, 코드베이스 검색, 명령어 실행, 작업 계획, 서브에이전트에게 위임

🧩 서브에이전트: 특화된 에이전트, 별도의 컨텍스트 창에서 실행, 자체 시스템 프롬프트와 도구 접근 권한 보유, 메인 에이전트에게 결과 반환

**에이전트 개념이 중요한 이유**

에이전트 추상화가 가능하게 하는 것:
책임의 분리, 컨텍스트 격리, 제어된 도구 권한, 병렬 작업 실행, 커스텀 특화
하나의 단일 AI 대화 대신, Claude Code는 다중 에이전트 아키텍처를 사용합니다.

## 25_claude_subagent.pdf

**서브에이전트란?**

서브에이전트는 Claude Code 내부에서 특정 유형의 작업을 처리하도록 설계된 특화된 AI 어시스턴트입니다.
각 서브에이전트는 자체 컨텍스트 창에서 실행됩니다:
커스텀 시스템 프롬프트, 특정 도구 접근, 독립적인 권한
서브에이전트는 부모 대화에서 Skills를 상속받지 않습니다.
Claude가 서브에이전트의 설명에 맞는 작업을 만나면 자동으로 해당 작업을 서브에이전트에게 위임하고, 서브에이전트가 실행 후 결과를 반환합니다.

**🧠 서브에이전트를 사용하는 이유**

서브에이전트는 다음 방식으로 워크플로를 개선합니다:
컨텍스트 보존: 상세한 탐색이나 구현을 메인 대화와 분리합니다.
제약 시행: 서브에이전트가 사용할 수 있는 도구를 제어합니다.
재사용 가능한 설정: 프로젝트나 팀 간에 서브에이전트를 공유합니다.
특화된 동작: 각 서브에이전트가 커스텀 프롬프트를 통해 집중된 전문성을 가질 수 있습니다.
비용 관리: 적절한 경우 더 저렴한 모델로 작업을 라우팅합니다.

**🚀 내장 서브에이전트**

Claude Code에는 자동으로 사용되는 내장 헬퍼가 포함됩니다:
Explore: 빠른 코드베이스 검색 및 분석 (Haiku; 읽기 전용 도구)
Plan: 계획 중 리서치 (메인 모델; 읽기 전용)
General-purpose: 복잡한 다단계 작업 (메인 모델; 전체 도구 접근)

**🛠 첫 번째 서브에이전트 만들기**

## 26_claude_agent_team.pdf

**에이전트 팀이란?**

에이전트 팀은 Claude Code 내에서 여러 에이전트를 정의하고 조율할 수 있게 해줍니다.
단일 어시스턴트를 사용하는 대신, 작업에서 협력하는 구조화된 에이전트 팀을 만들 수 있습니다.
각 에이전트는: 자체 역할, 자체 지시사항, 다른 책임에 특화 가능.
이를 통해 가능한 것: 구조화된 워크플로, 명확한 책임 분리, 더 복잡한 작업 오케스트레이션.

**에이전트 팀을 사용하는 이유**

에이전트 팀은 다음을 지원하도록 설계되었습니다:
다단계 워크플로, 역할 기반 협업, 책임 위임, 구조화된 문제 해결
모든 지시사항을 단일 어시스턴트에게 주는 대신, 다음과 같은 팀을 정의합니다:
한 에이전트는 계획을 담당, 다른 에이전트는 구현, 또 다른 에이전트는 검토
에이전트 팀은 조율 오버헤드를 추가하고 단일 세션보다 훨씬 더 많은 토큰을 사용합니다.

**에이전트 팀을 사용해야 할 때**

리서치와 검토: 여러 팀원이 문제의 다양한 측면을 동시에 조사하고 서로의 발견을 공유하고 도전할 수 있습니다.
새 모듈이나 기능: 팀원들이 서로 겹치지 않고 각자 별도의 부분을 담당할 수 있습니다.
경쟁 가설로 디버깅: 팀원들이 병렬로 다른 이론을 테스트하고 더 빠르게 답을 수렴합니다.
크로스 레이어 조율: 프론트엔드, 백엔드, 테스트에 걸친 변경사항을 각 팀원이 담당합니다.

**표시 모드**

In-process: 모든 팀원이 메인 터미널 내에서 실행됩니다. `Shift+Down`으로 팀원 간 전환하고 직접 메시지를 입력합니다. 어떤 터미널에서도 작동하며 추가 설정이 필요 없습니다.
Split panes: 각 팀원이 자체 창을 가집니다. 모든 팀원의 출력을 동시에 볼 수 있고 창을 클릭해 직접 상호작용할 수 있습니다. `tmux` 또는 `iTerm2`가 필요합니다.

`tmux`: 시스템의 패키지 매니저를 통해 설치합니다.
`iTerm2`: `it2` CLI를 설치한 후 iTerm2 Settings → General → Magic → Enable Python API에서 Python API를 활성화합니다.

**아키텍처**

Team lead: 팀을 생성하고, 팀원을 생성하며, 작업을 조율하는 메인 Claude Code 세션
Teammates: 각자 할당된 작업을 수행하는 별도의 Claude Code 인스턴스
Task list: 팀원들이 할당받고 완료하는 작업 항목의 공유 목록
Mailbox: 에이전트 간 통신을 위한 메시징 시스템

**에이전트 팀의 작동 방식**

에이전트 팀 사용 시:
작업이 시작됩니다.
팀이 어떤 에이전트가 응답해야 할지 결정합니다.
에이전트가 지시사항에 따라 역할을 수행합니다.
출력이 에이전트 간에 전달될 수 있습니다.
최종 결과가 제시됩니다.
워크플로는 구조화되어 있지만 설정 가능합니다.

**파일 구조**

에이전트 팀은 프로젝트의 파일을 사용하여 설정됩니다.
에이전트 정의 파일, 팀 설정 파일.
이 파일들이 Claude Code가 에이전트를 로드하고 오케스트레이션할 수 있게 합니다.
Team config: `~/.claude/teams/{team-name}/config.json`
Task list: `~/.claude/tasks/{team-name}/`

## 27_claude_plugin.pdf

**Plugins란**

Plugins는 Claude Code를 재사용 가능한 커스텀 기능(skills, agents, hooks, MCP/LSP 서버)으로 확장합니다.
프로젝트와 팀 간에 공유 가능하고 버전 관리됩니다.

**Plugins vs 독립 설정 사용 시기**

독립 설정은 실험에 쉽고; plugins는 재사용 가능하고 공유 가능한 패키지를 위한 것입니다.
Plugins는 네임스페이스 명령어를 사용합니다 (예: `/plugin-name:skill`)

**Plugin 빠른 시작**

Plugin 디렉토리 생성: `mkdir my-first-plugin`
Manifest 생성 (`plugin.json`): name, description, version, author 데이터.
Skills 추가: `skills/` 디렉토리에 마크다운으로 배치 (예: `SKILL.md`).
Plugin 테스트: `claude --plugin-dir ./my-first-plugin`을 사용한 후 명령어 트리거.

**Plugin 구조 개요**

`.claude-plugin/plugin.json` → Manifest.
`commands/` → 슬래시 명령어.
`agents/` → 커스텀 에이전트.
`skills/` → Skills 정의.
`hooks/` → 이벤트 자동화 핸들러.
`.mcp.json` → MCP (Model Context Protocol) 설정.
`.lsp.json` → 코드 인텔리전스를 위한 LSP (Language Server Protocol) 설정.
`settings.json` → plugin이 활성화될 때 적용되는 기본 설정.

**Plugins 개발**

Skills 추가: 각 skill은 `skills/<skill-name>/SKILL.md`에 위치합니다. Skills는 `$ARGUMENTS`를 받을 수 있습니다.
LSP 서버 지원: LSP 설정으로 코드 인텔리전스 기능(정의로 이동, 자동 완성 등)을 활성화합니다.
기본 설정: `settings.json`으로 기본 에이전트를 지정하여 plugin 동작을 재정의할 수 있습니다.

**로컬에서 Plugins 테스트**

`--plugin-dir`을 반복 사용하여 여러 plugin 디렉토리를 사용하세요.
`claude --plugin-dir ./my-plugin1 --plugin-dir ./my-plugin2`
각 컴포넌트(skills, agents, hooks 등)를 독립적으로 테스트합니다.

**디버깅**

올바른 구조 확인 (예: `.claude-plugin/` 내부에 없는 디렉토리).
문서의 CLI 도구와 디버그 명령어를 사용하세요.

**공유 및 배포**

문서(README) 추가.
시맨틱 버저닝 사용.
plugin 마켓플레이스에 게시합니다 (다른 사람들이 설치할 수 있도록).
`https://code.claude.com/docs/en/plugin-marketplaces`
게시 후 plugin 매니저 UI 또는 CLI를 통해 설치할 수 있습니다.

**변환 및 마이그레이션**

기존 공통 설정(`.claude/`)을 plugin으로 변환할 수 있습니다.
commands, agents, skills를 새 plugin 디렉토리에 복사하고 manifest를 정의하세요.

## 29_claude_simplify.pdf

**`/simplify`란**

`/simplify`는 Claude Code에서 변경 후 정리 명령어입니다.
최근 변경된 파일을 검토하고 다음을 찾습니다:
코드 재사용 기회 (중복 로직, 누락된 공유 헬퍼)
코드 품질 문제 (가독성, 구조, 유지보수성)
효율성 문제 (불필요한 작업, 성능 함정)
그런 다음 발견한 것들을 수정합니다.

**사용 시기**

무언가를 구현한 후 `/simplify`를 사용하세요:
기능 구현 완료 후, 버그 수정 후, PR 오픈 전 (빠른 "polish pass"로)
이렇게 생각하세요: "다 됐다! 이제 깔끔하고 탄탄하게 만들자."

**내부 작동 방식**

`/simplify`를 실행하면 Claude Code가:
3개의 검토 에이전트를 병렬로 생성합니다.
Agent A: 코드 재사용 검토자, Agent B: 코드 품질 검토자, Agent C: 효율성 검토자
발견사항을 집계하고, 겹치는 제안을 결합하며, 고영향 변경사항을 우선순위화합니다.
수정을 적용합니다 (단순한 코멘트가 아닌 직접 개선사항 구현).

**포커스 모드 (선택적 지시사항)**

가장 중요한 것을 강조하는 짧은 지시사항을 추가할 수 있습니다.
예시: `/simplify focus on memory efficiency`
이렇게 하면 검토자들이 메모리 관련 개선사항에 편향되도록 합니다 (예: 할당 줄이기, 큰 중간 구조 피하기, 관련 부분에서 스트리밍 vs 버퍼링).

**빠른 예시**

기본 정리: `/simplify`
특정 관심사 타겟팅:
`/simplify focus on memory efficiency`
`/simplify focus on removing duplication and improving readability`
`/simplify focus on hot-path performance`

## 30_claude_batch.pdf

**`/batch`란**

`/batch <instruction>`은 Claude Code의 대규모 리팩토링/마이그레이션 오케스트레이터입니다.
고수준 변경 요청을 주면 작업을 많은 독립적인 단위로 분할하여 코드베이스 전체에서 병렬로 실행합니다.

**사용 시기**

변경사항이 다음과 같을 때 `/batch`를 사용하세요:
광범위함 (많은 파일/모듈에 영향), 반복 가능함 (저장소 전체에 유사한 편집), 분해 가능함 (청크로 안전하게 분할 가능)
일반적인 예시:
프레임워크 마이그레이션 (예: Solid → React)
대규모 리팩토링 (패턴 이름 변경, 디렉토리 이동, 라이브러리 교체)
체계적인 코드베이스 업그레이드 (API 변경, 설정 표준화)

**입력 (제공해야 할 것)**

원하는 변경사항을 설명하는 단일 지시사항을 제공합니다.
예시: `/batch migrate src/ from Solid to React`
좋은 지시사항은: 범위에 대해 구체적 (어떤 폴더/모듈), 목표 상태 명확 ("완료"가 무엇을 의미하는지), 필요한 경우 제약사항 포함 (API 호환성 유지, 동작 변경 없음 등).

**`/batch` 작동 방식 (실행 모델)**

코드베이스 리서치 → 5~30개의 독립적인 단위로 분해 → 승인을 위한 계획 제시 → 제안된 단위와 접근 방식 검토 → 승인 전까지 아무것도 진행하지 않음.
승인 후 병렬 구현: 단위당 하나의 백그라운드 에이전트 생성, 각 에이전트는 격리된 git worktree에서 작업, 각 에이전트가 단위 구현 → 테스트 실행 → PR 오픈.

**핵심 개념**

단위를 통한 병렬성: `/batch`가 효과적인 이유는 "하나의 거대한 작업"을 동시에 실행할 수 있는 많은 작은 작업으로 바꾸기 때문입니다.

git worktree를 통한 격리: 각 에이전트가 별도의 worktree에서 작업하여 서로의 작업 디렉토리를 침범하지 않습니다. 로컬 충돌을 줄이고 단위별 변경사항을 깔끔하게 유지합니다.

사람 승인 체크포인트: 계획 검토 단계가 중요합니다: 불필요한 컴퓨팅/시간 낭비를 방지하고 범위와 위험이 원하는 것과 일치하는지 확인합니다.

단위당 PR 출력: 작업이 여러 PR로 제공됩니다. 검토를 관리 가능하게 하고, 단계적 병합을 허용하며, 필요한 경우 일부를 롤백할 수 있습니다.

**요구사항 및 제약사항**

git 저장소가 필요합니다.
5~30개의 의미 있는 청크로 분할할 수 있는 작업에 가장 적합합니다.
작업 항목이 너무 상호 의존적이면 병합 충돌이나 불안정한 중간 상태가 발생할 수 있습니다 — 계획과 순서가 중요합니다.

**예시 프롬프트**

`/batch migrate src/ from Solid to React`
`/batch replace deprecated API X with API Y across the repo, but preserve behavior`
`/batch standardize logging to use <new logger> and remove old logger usage`
`/batch rename all occurrences of FooService to BarService and update imports/tests`

## 31_claude_ralph.pdf

**Ralph Wiggum Plugin (`/ralph-loop`)**

"Ralph"는 지속적인 AI 에이전트 루프에 기반한 개발 방법론으로 설명됩니다 — 에이전트에게 프롬프트 파일을 반복적으로 피드백하여 완료될 때까지 반복적으로 개선하는 간단한 `while true` 개념입니다.
이 기법은 Ralph Wiggum (심슨 가족)의 이름을 따서 명명되었으며 지속적인 반복을 강조합니다.

**루프가 Claude Code에서 작동하는 방식**

plugin은 Claude의 종료 시도를 가로채는 Stop hook을 사용하여 Ralph를 구현합니다.
명령어를 한 번 실행하면 Claude Code가 루프를 반복합니다:
작업 수행 → 종료 시도 → Stop hook이 종료 차단 → Stop hook이 동일 프롬프트 재피드백 → 완료될 때까지 반복
루프는 현재 세션 내에서 실행됩니다 (외부 bash 루프 불필요). Stop hook은 `hooks/stop-hook.sh`에 위치하며 일반 세션 종료를 차단하여 자기 참조 루프를 만듭니다.

**명령어**

`/ralph-loop`: 현재 세션에서 Ralph 루프를 시작합니다.
`/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"` 옵션:
`--max-iterations <n>`: N번 반복 후 중지 (기본값: 무제한)
`--completion-promise <text>`: 완료를 알리는 문구
`/cancel-ralph`: 활성 Ralph 루프를 취소합니다.

**철학**

반복 > 완벽: 처음에 완벽을 목표로 하지 않습니다 — 루프가 개선합니다.
실패는 데이터: "결정론적으로 나쁜" 실패는 예측 가능하고 정보를 제공하며 프롬프트 튜닝에 사용할 수 있습니다.
운영자 스킬이 중요: 성공은 좋은 프롬프트 작성에 달려 있습니다.
지속성이 이깁니다: 계속 시도하세요 — 루프가 재시도 로직을 자동으로 처리합니다.

**Ralph를 사용해야 할 때**

좋은 경우: 명확한 성공 기준이 있는 잘 정의된 작업, 반복/개선 작업 (예: 테스트 통과), 자리를 비울 수 있는 그린필드 프로젝트, 자동 검증이 있는 작업 (테스트, 린터)

좋지 않은 경우: 사람의 판단이나 설계 결정이 필요한 작업, 일회성 작업, 불명확한 성공 기준, 프로덕션 디버깅

## 32_claude_ollama.pdf

**Ollama란?**

Ollama는 클라우드 API에 의존하지 않고 로컬 머신(Mac, Linux, Windows)에서 직접 대형 언어 모델을 실행할 수 있는 로컬 LLM 런타임입니다.

모델 다운로드(pull) → 로컬에서 실행 → CLI 또는 API를 통해 상호작용

**Ollama가 중요한 이유**

🔐 프라이버시 우선: 모든 데이터가 로컬 머신에 유지됩니다. OpenAI 같은 외부 서비스에 프롬프트를 보낼 필요가 없습니다.
⚡ 낮은 지연시간: 네트워크 호출 없음 → 더 빠른 응답 시간

🧪 개발자 친화적: 다양한 모델로 쉬운 실험

**모델 관리**

Ollama는 간단한 명령어로 모델을 다운로드합니다:

`ollama run llama3`

## 33_claude_channel.pdf

**채널이란?**

채널은 외부 시스템이 실행 중인 Claude Code 세션에 메시지를 보낼 수 있게 해줍니다.
세션이 활성화된 동안 실시간으로 작동합니다.
채팅, 알림, 웹훅 이벤트를 지원합니다.
자리를 비울 때도 Claude가 반응할 수 있게 합니다.

**핵심 개념**

기존 로컬 세션 내에서 실행됩니다. 새 세션을 만들거나 업데이트를 폴링할 필요가 없습니다.
요청-응답 대신 이벤트 기반 워크플로.
👉 "Claude에게 이벤트를 푸시하는 것"으로 생각하세요.

**작동 방식**

채널 plugin 설치 → `--channels`로 Claude Code 시작 → 외부 시스템이 메시지 전송 → Claude가 처리하고 응답 → 양방향 통신(채팅 브리지) 지원

**지원되는 채널**

Telegram, Discord, iMessage, MCP를 통한 커스텀 채널
Plugins는 설정 및 인증이 필요합니다.

**사용 사례 예시**

Claude에서 직접 CI/CD 알림 수신
핸드폰에서 Claude와 채팅
시스템 이벤트를 모니터링하고 즉시 반응

**보안 모델**

발신자 허용 목록 (승인된 사용자만 메시지를 보낼 수 있음)
인증을 위한 페어링 프로세스
접근 정책이 상호작용 가능한 사용자를 제어합니다
👉 신뢰할 수 있는 소스만 액션을 트리거할 수 있도록 보장합니다.

**엔터프라이즈 제어**

채널은 조직에서 기본적으로 비활성화됩니다.
관리자가 활성화해야 합니다.
허용되는 plugin을 제한할 수 있습니다.
👉 조직 수준에서 완전한 제어.

**중요한 이유**

실시간, 이벤트 기반 개발을 가능하게 합니다.
시스템 전반에 걸쳐 워크플로를 연결된 상태로 유지합니다.
수동 모니터링을 줄입니다.
Claude를 라이브 자동화 에이전트로 변환합니다.
👉 채널은 Claude Code를 단순한 도구에서 지속적으로 실행되는 반응형 시스템으로 변환합니다.

## 34_claude_harness.pdf

**Claude Code는 왜 다른가?**

에이전트 = 모델(Anthropic) + Harness(여러분)
Harness는 Claude를 똑똑하게 만드는 것이 아닙니다.
Claude는 이미 똑똑합니다.
Harness는 Claude에게 손, 눈, 작업공간을 줍니다.

2025년 2월 출시 → 2026년 초 $1B ARR → 2026년 3월: npm 소스맵 유출로 50만 줄의 TypeScript 노출
사람들을 놀라게 한 것은 모델이 아니었습니다 — harness 아키텍처였습니다.

**Harness란?**

Tool Dispatch (도구를 실제로 실행), Context Management (컨텍스트 창 관리), Permission Gating (권한 경계), State Persistence (세션 저장), Error Recovery (실패에서 복구)

**Claude Code Harness의 6계층 아키텍처**

핵심 원칙: 각 계층은 별개의 책임을 가집니다. 하위 계층 = 안정적 / 상위 계층 = 유연. 모든 것을 하나의 계층에 욱여넣기 = 실패.

**계층 1-2 — CLAUDE.md와 Skills**

`CLAUDE.md`, Skill 구조, `SKILL.md` frontmatter

**계층 3 — Hooks (결정론적 가드레일)**

Hook 이벤트:
`PreToolUse`: 도구 호출 직전
`PostToolUse`: 도구 호출 직후
`UserPromptSubmit`: 사용자 입력 제출 시
`Stop`: 세션 종료
`SubagentStop`: 서브에이전트 종료

Hooks가 필요한 이유:
LLM은 비결정론적; Hooks는 결정론적
프롬프트로 요청 ≠ 강제 실행
프롬프트 위반 비용 = 0; Hook 위반 비용 = exit 1

**계층 4 — 서브에이전트 (컨텍스트 경제학)**

서브에이전트 정의 (`.claude/agents/code-reviewer.md`)

주의사항 (Shrivu Shankar 블로그에서):
❌ 서브에이전트는 컨텍스트를 숨겨 메인이 전체적 추론을 잃습니다
❌ 사람이 설계한 경직된 워크플로를 모델에 강제합니다
✅ Master-Clone 패턴: 컨텍스트를 `CLAUDE.md`에 넣고, 메인 에이전트가 동적으로 위임하게 합니다

**계층 5-6 — 에이전트 팀 & Plugins**

에이전트 팀: Generator-Evaluator 패턴 (Anthropic Labs)
Plugin 구조 및 배포

**MCP — Harness와 외부 세계의 경계**

MCP 역할의 변화 (2025 → 2026)

Shrivu의 규칙: "내가 아직 사용하는 유일한 MCP는 Playwright용입니다" — MCP는 복잡하고 상태가 있는 환경에만 사용

Claude Code에서 MCP 설정:
`claude mcp add playwright npx @modelcontextprotocol/server-playwright`
`claude mcp list`

**점진적 도입 전략 (HumanLayer의 "배포 지향" 마인드셋)**

1일차: `CLAUDE.md`만 작성
1주차: 반복되는 프롬프트 → Skills
2주차: 잊어버리는 체크리스트 → Hooks
1개월차: 컨텍스트를 오염시키는 작업 → 서브에이전트
2개월차: 팀과 공유 → Plugins

**핵심 원칙 & 안티 패턴**

해야 할 것 ✅: 에이전트가 실패한 후에 harness를 설계하세요, 실패 전이 아닙니다. 정책(`CLAUDE.md`) / 절차(Skills) / 시행(Hooks)을 분리하세요. 결정론적 검사 → Hooks; 판단 호출 → LLM. 반복되는 패턴에만 서브에이전트 사용. CLI + bash > 복잡한 MCP.

하지 말아야 할 것 ❌: 모든 것을 `CLAUDE.md`에 욱여넣기. 선제적 최적화 (해결할 문제 찾아 헤매기). 검토 없이 레지스트리에서 skills 설치. 서브에이전트 미세 최적화. 첫 날부터 에이전트 팀 구축.
