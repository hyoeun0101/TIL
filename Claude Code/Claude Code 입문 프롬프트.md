### 프로젝트 파악
```text
이 코드베이스의 전체 구조를 개괄적으로 설명해줘.
여기서 사용된 주요 아키텍처 패턴을 설명해줘.
핵심 데이터 모델이 무엇인지 정리해줘. 
```

### 관련 파일 찾기
```text
사용자 인증을 처리하는 파일들을 찾아줘.
이 인증 관련 파일들이 서로 어떻게 연결되어 동작하는지 설명해줘.
프론트엔드부터 데이터베이스까지 로그인 흐름을 추적해서 설명해줘.

```

### 작은 수정 요청
```text
메인 인증 파일에 로그인 흐름을 설명하는 짧은 주석을 추가해줘.
동작은 바꾸지 말고, auth 모듈에서 헷갈리는 변수명을 더 이해하기 쉽게 바꿔줘.
로그인 핸들러에 null 체크가 빠져 있다면 안전하게 추가해줘.
```

### 검증 요청
```text
관련 테스트를 실행하고 무엇이 바뀌었는지 요약해줘.
이번 변경이 기존 동작을 깨뜨리지 않는지 확인해줘.
```

### 완성형 프롬프트
```text
이 프로젝트를 읽고 전체 구조를 먼저 요약해줘.
그다음 인증과 관련된 파일들을 찾아서 서로 어떻게 동작하는지 설명해줘.
이후 auth 흐름에서 위험이 낮은 작은 개선점이 하나 있으면 적용해줘.
마지막으로 관련 테스트나 체크를 실행해서 정확히 무엇이 바뀌었는지 정리해줘.
```

### 프롬프트 스타일
```text
[무엇을 볼지]
src/auth/ 아래 파일들을 중심으로 봐줘.

[무엇을 원하는지]
로그인 흐름을 설명하고, 위험이 낮은 개선점이 있으면 하나만 적용해줘.

[제약]
동작은 바꾸지 말고, 작은 수정만 해줘.

[검증]
관련 테스트나 체크를 실행해서 결과를 함께 알려줘.
```

사용자 인증을 처리하는 파일들을 찾아줘.

```text
프론트엔드부터 데이터베이스까지 로그인 흐름을 추적해서 설명해줘.

src/auth/ 아래 파일들만 기준으로 로그인 흐름을 요약해줘.

### 5) 진입점 찾기

이 프로젝트에서 서버 시작 지점과 주요 API 라우팅 진입점을 찾아줘.
```

Claude Code는 파일 읽기, 검색, 실행 같은 도구를 조합해 이런 탐색을 수행한다.

# 작은 수정 시킬 때

### 1) 안전한 작은 개선 1개

```text
이 코드에서 위험이 낮고 바로 적용 가능한 작은 개선점 하나만 찾아서 수정해줘.
```

### 2) 주석 추가

```text
메인 인증 파일에 로그인 흐름을 설명하는 짧은 주석을 추가해줘.
```

### 3) 변수명 정리

```text
동작은 바꾸지 말고, auth 모듈에서 헷갈리는 변수명을 더 이해하기 쉽게 바꿔줘.
```

### 4) 방어 코드 추가

```text
로그인 핸들러에 null 체크가 빠져 있다면 안전하게 추가해줘.
```

작은 범위의 수정은 굳이 복잡한 계획 모드 없이 바로 요청해도 된다. 모범 사례 문서도 **작고 명확한 변경은 직접 시키고**, 큰 변경이나 불확실한 작업에서만 계획을 권장한다.

# 버그 잡을 때

### 1) 버그 원인 후보 찾기

```text
세션 만료 후 재로그인이 실패할 가능성이 있는 지점을 후보별로 설명해줘.
```

### 2) 재현부터 시키기

```text
로그인 실패 문제를 재현할 수 있는 테스트를 먼저 만들고, 그다음 수정해줘.
```

### 3) 실패한 테스트 기준으로 고치기

```text
실패한 테스트를 확인하고, 근본 원인을 찾아서 수정한 뒤 다시 테스트를 돌려줘.
```

공식 워크플로우는 오류를 공유하고, 수정 제안을 받고, 변경을 적용하는 식으로 안내한다. 또 모범 사례는 **증상만 말하지 말고 재현 기준과 검증 방법을 함께 주라**고 강조한다.

# 테스트와 검증

### 1) 테스트 부족한 부분 찾기

```text
이 모듈에서 테스트가 부족한 함수나 엣지 케이스를 찾아줘.
```

### 2) 테스트 추가 후 검증

```text
관련 테스트를 추가하고 실행한 뒤, 무엇이 바뀌었는지 요약해줘.
```

공식 예시에도 **테스트되지 않은 코드 찾기 → 테스트 추가 → 엣지 케이스 추가 → 테스트 실행 및 실패 수정** 흐름이 나온다.

# 계획이 필요한 큰 작업

### 1) 큰 변경은 먼저 계획

```text
바로 수정하지 말고, 먼저 이 기능 변경에 필요한 파일들과 작업 순서를 계획으로 정리해줘.
```

복잡한 변경은 Plan Mode가 적합하다. 세션 중 Shift+Tab으로 전환하거나, 처음부터 `claude --permission-mode plan`으로 시작할 수 있다.

# 바로 써먹는 완성형 프롬프트 5개

아래 5개는 특히 실전성이 높다.

### A. 새 프로젝트 들어갔을 때

```text
이 프로젝트를 읽고 전체 구조를 요약해줘.
핵심 디렉터리, 주요 데이터 흐름, 자주 건드리게 될 파일들을 초보자 기준으로 설명해줘.
```

### B. 특정 기능 파악할 때

```text
src/auth/를 중심으로 로그인과 세션 관련 흐름을 설명해줘.
관련 파일 목록과 각 파일의 역할도 같이 정리해줘.
```

### C. 작은 개선 하나만 할 때

```text
auth 흐름에서 위험이 낮은 작은 개선점 하나만 골라서 적용해줘.
동작은 바꾸지 말고, 변경 이유와 영향 범위도 설명해줘.
```

### D. 버그 수정할 때

```text
세션 만료 후 로그인 실패가 날 수 있는 원인을 찾아줘.
재현 가능한 테스트를 먼저 만들고, 수정 후 관련 테스트를 다시 실행해줘.
```

### E. 큰 작업 시작 전

```text
바로 코드는 수정하지 말고, 먼저 구현 계획을 세워줘.
어떤 파일을 왜 건드려야 하는지, 테스트는 무엇을 확인해야 하는지 포함해줘.
```

# 입문자에게 특히 중요한 3가지

첫째, **파일 경로를 같이 써라**
예:

```text
src/auth/login.ts를 중심으로 봐줘.
```

둘째, **제약 조건을 같이 써라**
예:

```text
동작은 바꾸지 말고, 가독성만 개선해줘.
```

셋째, **검증을 꼭 붙여라**
예:

```text
관련 테스트를 실행하고 결과를 알려줘.
```

이 세 가지가 프롬프트 품질을 크게 올린다. 문서도 특정 파일, 시나리오, 테스트 기준을 함께 주는 게 효과적이라고 강조한다.

# 입문 후 바로 배우면 좋은 명령 4개

### `/init`

프로젝트용 `CLAUDE.md` 초안을 자동 생성한다. 빌드 명령, 테스트 지침, 프로젝트 규칙을 잡는 시작점으로 권장된다.

### `/agents`

사용 가능한 subagent를 보고 만들 수 있다. 공식 워크플로우에도 입문 이후 단계로 소개된다.

### `/loop`

세션이 열려 있는 동안 반복 체크를 걸 수 있다. 예: 배포 완료 확인.

### `claude --permission-mode plan`

복잡한 작업을 수정 전에 읽기 전용으로 분석하게 할 수 있다.
