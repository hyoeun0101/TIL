- 직렬화? 자바 객체 -> 바이트 스트림, ObjectOutputStream 사용하여 직렬화한다.
- 역직렬화? 바이트 스트림 -> 자바 객체, ObjectInputStream 사용하여 역직렬화한다.

### 🍎 Item85. 자바 직렬화의 대안을 찾으라
- ObjectOutputStream 사용하지마라.
- 자바 직렬화의 위험성. 
    - 보이지 않는 생성자. ObjectOutputStream의 readObject()
    - API와 구현 사이의 모호해진 경계
    - 잠재적인 정확성 문제
    - 성능, 보안, 유지보수 등
- ObjectInputStream의 readObject메서드는 거의 모든 타입의 객체를 만들어낼 수 있다. 이는 거의 모든 코드를 대신 수행할 수 있으며, 곧 모든 코드가 공격 범위에 들어갈 수 있음을 뜻한다.
- 직렬화의 위험을 회피하는 방법
    - 가장 좋은 건 아무것도 역직렬화 하지마라.
    - 어쩔 수 없이 써야한다면 신뢰할 수 있는 데이터만 역직렬화하라.
- 직렬화를 피할 수도 없고, 역직렬화한 데이터도 신뢰할 수 없는 경우엔 java.io.ObjectInputFilter(자바 9에 추가됨)를 사용하라.
    - java.io.ObjectInputFilter : 데이터 스트림이 역직렬화되기 전 필터링함. 화이트리스트 방식을 사용하여 따로 기록해둔 안전한 클래스만 수용하도록 한다.

```
[정리]
- 자바 직렬화는 위험하다. 그러니 자바 직렬화 대신 JSON이나 프로토콜 버퍼를 사용하라.
- 신뢰할 수 없는 데이터는 절대 역직렬화하지 말고, 해야 하는 경우라면 객체 역직렬화 필터를 사용하라. (하지만 이마저도 모든 공격을 막아줄 수 없음을 염두에 둘 것.)
```

### 🍎 Item86. Serializable을 구현할지는 신중히 결정하라

- 클래스의 인스턴스를 직렬화하려면 클래스에 implements Serializabe만 덧붙이면 된다. 직렬화를 지원하기란 쉬워 보이지만 이는 아주 값비싼 일이다.
- Serializable 구현의 문제점
    1. 릴리스한 뒤에는 수정하기 어렵다.
    2. 숨은 생성자로 인해 버그와 보안 구멍이 생길 위험이 높아진다. 
    3. 해당 클래스의 신버전을 릴리스할 때 테스트할 것이 늘어난다.
- Serializable 구현 여부는 결코 쉽게 결정할 사안이 아니다.

```
[정리]
노출될 가능성이 없거나, 보호된 환경에서만 쓰일 데이터가 아니라면 Serializalbe 구현은 신중히 해야 한다.
```

### 🍎 Item86. 커스텀 직렬화 형태를 고려해보라

- 객체의 물리적 표현과 논리적 표현의 차이가 클 때 기본 직렬화 형태를 사용하면 발생하는 문제점 4가지
    1. 공개 API가 현재의 내부 표현 방식에 영구히 묶인다.
    2. 너무 많은 공간을 차지할 수 있다. 필요없는 내부 구현도 직렬화한다. 
    3. 시간이 너무 많이 걸린다.
    4. 플랫폼에 따라 스택 오버플로가 발생할 수 있다.

```
[정리]
자바의 기본 직렬화 형태는 객체를 직렬화한 결과가 해당 객체의 논리적 표현과 일치할 때만 사용하라. 그렇지 않으면 커스텀 직렬화 형태를 고안하라.
```

### 🍎 Item87. readObject 메서드는 방어적으로 작성하라
- ObjectInputStream의 readObject 메서드는 바이트 스트림을 받는 생성자라 할 수 있다. 따라서 생성자와 똑같은 주의를 기울일 필요가 있다.
    - 인수 유효성 검사, 매개변수 방어적 복사 등의 주의가 필요.
- 클래스를 불변으로 작성했더라도 readObject()에서 주의를 기울이지 않으면 해당 클래스는 가변이 될 수 있다. 따라서 readObject()에서 반드시 방어적 복사를 해야 한다.

- 안전한 readObject 메서드 작성하는 법
    1. private 객체 참조 필드는 각 필드가 가르키는 객체를 방어적 복사하라. 
    2. 모든 불변식을 검사하여 어긋나는 게 있다면 InvalidObjectException을 던져라. 방어적 복사 다음에는 반드시 불변식 검사를 해야 한다.
    3. 역직렬화한 객체 전체를 유효성 검사해야 한다면 ObjectInputValidation 인터페이스를 사용하라.
    4. 직접적이든, 간접적이든 재정의할 수 있는 메서드는 호출하지 마라.



### 🍎 Item88. 인스턴스 수를 통제해야 한다면 readResolve보다는 열거 타입을 사용하라.
- Serialiable을 구현하면 더이상 싱클턴이 아니게 된다. readObject 메서드를 사용하면 새로운 인스턴스를 반환하기 때문이다.
- readResolve 메서드를 사용하면 readObject 메서드가 만든 인스턴스를 기존의 싱글톤 인스턴스를 반환할 수 있다. 하지만 readResolve 메서드를 인스턴스의 통제 목적으로 이용한다면 모든 필드는 transient로 선언해야 한다.

- 싱글턴을 보장해야 하는 클래스를 Enum으로 구현하라. 선언한 상수 외에 다른 객체가 없음을 보장해주기 때문이다.

### 🍎 Item89. 직렬화된 인스턴스 대신 직렬화 프록시 사용을 검토하라.
- Serializable을 구현하면 생성자 이외의 인스턴스 생성 방법이 생기므로 버그와 보안 문제가 발생할 가능성이 커진다. 직렬화 프록시 패턴을 사용하면 위험성을 크게 줄일 수 있다.
- 직렬화 프록시 패턴
    1. 바깥 클래스의 논리적 상태를 정밀하게 표현하는 중첩 클래스를 private static으로 선언한다. 이 중첩 클래스가 바깥 클래스의 직렬 프록시다.
    2. 중첩 클래스의 생성자는 단 하나여야 하며, 바깥 클래스를 매개변수로 받아 데이터를 복사한다. (일관성 검사나 방어적 복사 필요X)
    3. 바깥 클래스와 중첩 클래스 모두 Serializable을 구현한다고 선언한다.
    4. 바깥 클래스에 중첩 클래스의 인스턴스를 반환하는 메서드를 선언한다. 이 메서드는 직렬화할 때 바깥 클래스 대신 직렬화 프록시를 반환한다.


```
[정리]
제 3자가 확장할 수 없는 클래스라면 가능한 한 직렬화 프록시 패턴을 사용하자.
이 패턴이 불변식을 안정적으로 직렬화해주는 가장 쉬운 방법일 것이다.
```
