### 🍎 Item 49. 매개변수가 유효한지 검사하라.
```
메서드나 생성자의 매개변수에 어떤 제약이 있을지 생각해야 한다. 그 제약을 문서화하고, 메서드 코드 시작 부분에서 유효성 검사를 해야 한다.
```
- 메서드나 생성자의 매개변수의 값은 특정 조건을 만족해야 한다.(인덱스 값은 음수 X, 객체 참조는 null이 X)
- 그 특정 조건은 반드시 문서화해야 하며, 메서드의 핵심 로직이 시작되기 전에 매개변수의 유효성을 검사해야 한다.
- public, protected 메서드
    - 올바른 매개변수가 아닐 때 던지는 예외를 문서화해야 한다. @throws 자바 독 태그를 사용한다.
```java
/**
 * @param m 계수(양수여야 한다.)
 * @return 현재 값 mod m
 * @throws ArithmeticException m이 0보다 작으면 발생한다.
 */
public BigInteger mod(BigInteger m) {
    if(m.signum() <= 0) {
        throw new ArithmeticException("계수(m)는 양수여야 합니다." + m);
    }
    ...
}

``` 
- Objects.requireNonNull로 매개변수 검사하기
```java
// strategy가 null이면 "전략" 메세지 예외 던짐.
this.strategy = Objects.requireNonNull(strategy, "전략");
```
- assert 단언문을 사용하여 매개변수 유효성 검증하기.
```java
private static void sort(long a[], int offset, int length) {
    assert a != null;
    assert offset >= 0 && offset <= a.length;
    assert length >= 0 && length <= a.length - offset;
    ...
}
```

- 메서드의 핵심 로직 실행 전 매개변수 유효성을 검사하지 않아도 되는 경우
    - 유효성 검사 비용이 지나치게 높거나 실용적이지 않을 때
    - 계산 과정에서 암묵적으로 검사가 실행될 때

### 🍎 Item50. 적시에 방어적 복사본을 만들어라.
```
클라이언트로부터 받는 요소, 클라이언트에게 반환하는 요소가 가변이라면 그 요소는 반드시 방어적 복사를 해야 한다.
단 복사 비용이 너무 크거나 클라이언트가 그 요소를 신뢰한다면 방어적 복사 대신 그 요소를 수정했을 때의 책임은 클라이언트에게 있음을 문서에 명시해라.
```

- 외부에서 클래스의 내부의 값을 변경해선 안된다. 따라서 방어적 복사를 사용하여 클라이언트가 클래스의 내부를 변경하지 못하도록 막아야 한다!
- 방어적 복사? 외부에서 클래스의 내부값을 변경하지 못하도록 막는 것.

```java
// 불변으로 보여도 변경될 수 있음.
public final class Period {
    private final Date start;
    private final Date end;

    /**
     * @param start 시작 시각
     * @param end 종료 시각. start보다 뒤여야 한다.
     * @throws IllegalArgumentException start가 end보다 늦을 때 발생한다.
     * @throws NullPointerException start나 end가 null이면 발생한다.
     */
    public Period(Date start, Date end) {
        if(start.compareTo(end) > 0) {
            throw new IllegalArgumentException(start+" after "+end);
        }
        this.start = start;
        this.end = end;
    }
    public Date getStart() {return start;}
    public Date getEnd() {return end;}
}

...

Date start = new Date();
Date end = new Date();

Period p = new Period(start, end);
end.setYear(78); //p의 내부를 수정했다!
```

```java
// 방어적 복사하기
// 반드시 매개변수의 유효성 체크 전에 방어적 복사본을 만들고, 복사본으로 유효성 체크를 하라.
// 원본 객체를 먼저 유효성 체크하면, 멀티스레딩 환경에선 다른 쓰레드에서 원본 객체를 수정할 위험이 있다.
public Period(Date start, Date end) {
    // 생성자에선 방어적 복사에 clone을 사용해선 안된다!
    this.start = new Date(start.getTime());
    this.end = new Date(end.getTime());

    if(start.compareTo(end) > 0) {
        throw new IllegalArgumentException(this.start+" after "+this.end);
    }
}

...

Date start = new Date();
Date end = new Date();
Period p = new Period(start, end);
p.getEnd().setYear(78); // 하지만 아직도 p의 내부를 변경할 수 있다!
```

```java
// 필드를 반환할 때도 방어적 복사를 한다. 이제 Period는 완벽한 불변이다!
// 반환할 때 실제 필드의 값을 반환하지 않으므로 외부에서 필드의 값을 변경할 수 없다.
// 접근자 메서드에선 방어적 복사에 clone을 사용해도 된다.
public Date getStart() {
    return new Date(start.getTime()); 
}

public Date getEnd() {
    return new Date(end.getTime());
}
```
- 자바8 이후에 Date 대신 Instant, LocalDateTime, ZonedDateTime을 사용하면 된다. Date는 낡은 API이니 사용하지 말자.
- 방어적 복사는 성능 저하가 따르고, 항상 쓸 수 있는건 아니다.
- 클라이언트가 클래스의 내부를 수정하지 않는 걸 확신할 때, 또는 불변식이 깨지더라도 그 영향이 클라이언트에게만 있을 때 방어적 복사를 생략할 수 있다.
- 방어적 복사를 생략한다면 해당 객체를 수정하지 말아야함을 문서화해야 한다.

### 🍎 Item51. 메서드 시그니처를 신중히 설계하라.
```
메서드는 신중히 작성해야 한다. 메서드 이름을 신중히 짓고, 매개변수 개수는 짧게 설계하라.
```
- 메서드 이름을 신중히 짓자.
- 무분별하게 너무 많은 메서드를 만들지 말자.
- 매개변수 목록은 짧게 유지하자. 4개 이하가 좋다.
- 매개변수가 너무 길 때 해결방법
    1. 매개변수의 목록을 부분집합으로 받도록 여러 메서드로 쪼개기.
    2. 매개변수 목록을 묶어주는 도우미 클래스를 만들기.
    3. 빌더 패턴 응용하기
- 매개변수 타입으론 클래스보단 인터페이스가 낫다. (HashMap보단 Map)
- 매개변수가 boolean보단 원소 2개짜리 enum 타입이 낫다.

### 🍎 Item52. 다중정의(오버로딩)는 신중히 사용하라.
```
매개변수 수가 같을 떄는 오버로딩을 피하라. 그게 불가피하다면 오버로딩된 메서드를 호출할 때 매개변수는 명시적으로 형변환해줘야 한다.
```
- 매개변수의 개수가 같은 오버로딩은 혼동을 일으키므로 만들지 마라!
    - List<E>의 remove(Object), remove(int)
- 매개변수의 개수가 같더라도 각각의 매개변수가 명확히 구분된다면 헷갈리지 않으니 상관없다.
    - ArrayList에는 int를 받는 생성자와 Collection을 받는 생성자가 있는데 헷갈릴 일은 없다.
- 오버로딩하는 대신 메서드 이름을 다르게 지어라.
    - ex) ObjectOutputStream의 writeInt, writeBoolean, writeLong
