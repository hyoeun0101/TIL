## 🔴 1. Why Clean Code?
- 코드는 한 번 작성되면 최소 10번 이상 읽힌다. 읽기 편하도록 작성하자.

- 대부분 개발자들의 주 업무는 남이 작성된 코드를 읽고 수정하고, 기능을 추가하는 일이다. 누구나 읽기 쉽도록 클린 코드를 작성해야 한다.

## 🔴 2. Why OOP?
- 절차지향
    - 프로시저가 순서대로 동작을 할 때 데이터를 공유하며 처리한다.

    - 데이터가 어디서 수정되고, 어떻게 동작하는지 알기 어렵다.
    - 하나의 수정으로 인해 side effect가 발생한다. 수정하기 어렵다.
    - 단순한 프로그램을 작성할 땐 유용하다.
    - 하지만 우리가 만드는 대부분의 프로그램은 로직이 복잡하다!

- 객체지향
    - 객체마다 데이터를 가지고 있다. 데이터와 코드가 캡슐화되어 있다.

    - 코드의 변경이 외부에 영향을 미치지 않는다. 

    - 예를 들어 A 객체가 B 객체를 사용할 때 interface로 사용해야 한다. 그럼 B가 변경되더라도 A의 변경은 일어나지 않는다.
    - 높은 응집도, 낮은 결합도

- 단순한 프로그램을 작성할 땐 절차지향이 유용하다. 하지만 우리가 만드는 대부분의 시스템은 계속 바뀌며, 로직은 복잡하다. 따라서 OOP가 유용하다.

## 🔴 3. Object, Role, Responsibility
- 객체의 이름 : '어떻게'로 정의하지 말고 **'무엇'으로 정의하자.**
    - ex) JsonRequestParser는 어떻게로 정의한 것이다. 이 이름은 Request를 어떻게(Json으로) 파싱할 것인가를 나타낸다.'어떻게'는 변경될 수 있다.
    - 따라서 RequestParser처럼 '무엇을' 파싱할 것인가로 바꿔야 한다.
    - ex) ArticleController, ArticleService는 잘못된 네이밍이다. Domain Driven. WriterService가 맞음.
    - 객체를 볼 때 데이터로 보는게 아니라 기능으로 바라봐야 한다.

- **역할**은 **책임의 집합**이다.
    - 역할 = 책임 + 책임 + 책임
    
- 객체는 역할을 가진다.






## 🔴 4. 객체지향 설계 과정
- 요구 사항이 모두 정의됐을 때.

1. 기능을 제공할 객체를 선별한다.(정적 설계)
    - 내부에서 필요한 데이터를 선별하여 클래스 다이어그램을 그린다. (ERD 같은)

2. 객체 간 메시지 흐름을 연결한다. (동적 설계)
    - 커뮤니케이션 다이어그램, 시퀀스 다이어그램 활용
    - 데이터를 가지고 있는 클래스들 간에 어떤 메시지를 주고 받아야 할까.

3. 1번 2번을 반복한다.

- 예시) 파일 암호화
- 하지만 보통은 FileReader, FileWriter, Encrypter등의 로직을 클래스로 빼지 않는다. FlowController의 내부의 function으로 둔다.

- 처음부터 객체지향 구조를 짜기란 쉽지 않으니 점점 리팩토링을 하면된다.

## 🔴 5. 캡슐화(Encapsulation)

- 내부 구현을 캡슐화하면 내부 구현을 변경하더라도 **client는 변경되지 않는다.**

- **Tell, Don't Ask**
    - 보통은 객체의 내장을 깐다.

```java
// 객체의 내장을 깜.
if (member.getExpiredDate().getTime() < System.currentTimeMillis>) {}

// 객체의 내장을 캡슐화화. expire 조건이 변경되더라도 외부 변경이 없음.
if (member.isExpired()) {}

```

- **Law of Demeter**

- **CQS(Command Query Separation)**
    - Command(Tell). 객체의 내부 변경.
    
    - Query(Ask): 객체의 상태 제공. 객체의 상태를 변경 X.

    - Command와 Query를 분리하자.

## 🔴 6. 다형성(Polymorphism)

- 다양한 형을 가질 수 있다. 

- java의 다형성 두가지
    - implements(구현)
    - extends(상속)

- 흔한 오해: **상속이 다형성, 재사용이다다** 
    - 공통 기능을 슈퍼 클래스에 정의하고, 이를 상속받으면 공통 기능을 재사용할 수 있다.
    - 하지만 상속은 변경할 수 없다. 수퍼 클래스의 변경이 다수의 서브 클래스에 영향을 미친다.
    - 상속은 강한 의존도를 가진다.

- **인터페이스가 다형성이고, 이것이 재사용이다.**

- Q. Servie 단에 왜 interface를 써야하나요? 어짜피 구현체 하나밖에 없는데.

- 토비의 스프링에 나오는 interface를 써야하는 이유 4가지
    1. 변경이 안되는 코드는 없다. 그러니 인터페이스를 써야 한다.

    2. 인터페이스를 사용해야 테스트하기 쉽다.
    3. 인터페이스를 사용하면 부가기능을 넣기 쉽다. 데코레이터 패턴 가능.
    4. **인터페이스를 사용하는 코드는 재사용이 된다.** 즉 변경이 필요없다.
        - 구현체가 추가되던 변경되던 client는 변경 X
