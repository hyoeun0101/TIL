- 동기화 기법
    - 상호배제 - 뮤텍스 - Lock 매커니즘
    - 세마포어 - 신호 매커니즘
    - 자바의 모니터 - 상호배제(뮤텍스)와 협력(조건변수)을 제공
    - 스핀락 - busy waiting

## 통기화 기법 1: 상호 배제 (Mutual Exclusion) = 뮤텍스
- 임계영역엔 Lock을 가진 스레드만 접근할 수 있다. Lock을 가진 스레드를 제외한 다른 스레드는 해당 임계영역에 접근하지 못하도록 배제한다.
- 뮤텍스는 상호배제를 구현한 도구이다.

### 1-1. 뮤텍스
- 뮤텍스는 락 매커니즘을 사용한다.
- Lock을 가진 스레드만 임계영역에 접근 가능하다. Lock을 획득한 스레드가 Lock을 해제하면 대기 중이던 다른 스레드가 Lock을 획득하여 임계영역에 접근한다.
- Mutex 객체의 플래그 = Lock

```java

do{

    acquired(mutex) // 락 획득

    // critical section

    release(mutex) // 락 해제

} while(true);
```

- java에서 뮤텍스 클래스는 제공하지 않지만 뮤텍스 원리를 사용한 동기화 기법을 제공함.

### 1-2. 뮤텍스 문제점

- 데드락 : 두 개 이상의 스레드들이 서로가 점유한 임계영역을 접근하려고 해서 상호적으로 블로킹되고, 이로 인해 아무 작업도 수행하지 못하는 상태가 됨.
- 우선순위 역전
- 오버헤드
- 성능 저하
- 잘못된 사용

## 동기화 기법 2: Semaphore (세마포어)

- 세마포어는 신호전달 메커니즘 동기화 도구이다.
- 정수형 변수 S, 원자적 함수 P, V로 구성된다.
- java.util.concurrent 패키지에 세마포어 클래스 제공함.

### 2-1. 세마포어 작동방식

- `S` : 정수형 변수. 공유 자원 개수(S)만큼 스레드의 접근이 허용됨.
- `P` : S가 1 감소(S--). 임계영역 진입 가능한지 판단하는 역할. wait 연산
- `V` : S가 1 증가(S++). 대기 중인 프로세스를 깨우는 역할. signal 연산.

- S가 0보다 크면 공유자원 접근 가능. S가 0이면 공유자원 접근 불가능.
- P, V는 원자적 실행이 보장되어야 함. 즉 synchronized 필요.

```java

do{
    P(S);

    // critical section

    V(S);
    
} while(true);

```

### 2-2. 세마포어 유형

- `이진 세마포어` : S가 1
    - 세마포어를 뮤텍스의 락 매커니즘처럼 사용.
- `카운팅 세마포어` : S가 2 이상
    - 자원 풀, 컬렉션의 크기 제한할 때 사용.
    - 락을 획득한 스레드와 락을 해제한 스레드가 다를 수 있음. 락이 아닌 신호를 전달하는 방식으로 동작함.

### 2-3. 프로세스 순서화(Ordering)

- 세마포어는 스레드 간 프로세스 흐름을 순서화할 수 있게 해준다.

### 2-4. 뮤텍스와 세마포어

|       | 뮤텍스                                         | 세마포어                                       |
|-------|---------------------------------------------|--------------------------------------------|
| 동작 방식 | 상호배제를 위한 동기화 기법. Lock 매커니즘                  | 카운팅 기법. 특정 개수의 스레드가 임계영역에 접근 가능.           |
| 소유권   | 소유권 있음. 락을 획득한 스레드만이 락을 해제할 수 있음.           | 소유권 없음. 세마포어를 사용하는 스레드는 모두 세마포어를 해제할 수 있음. |
| 초기값   | 기본적으로 잠겨있음.                                 | 초기값 설정할 수 있음.                              |
| 사용 목적 | 상호 배제를 위해. 하나의 자원에 하나의 스레드만 접근 가능하도록 하기 위함. | 한정적인 리소스의 사용을 제어하기 위함.                     |


- 자바에서는 뮤텍스를 고도화한 `모니터 객체`와 `세마포어 구현체`를 제공하고 있다.

## 동기화 기법 3: 모니터

- 뮤텍스, 세마포어보다 더 고수준의 동기화 기법.
- 모든 자바 객체는 기본적으로 모니터를 가지고 있음.
- 여러 스레드가 객체의 임계 영역에 진입하려고 하면 JVM은 모니터를 사용하여 스레드 간 동기화를 제공한다.
- 자바의 모니터는 상호 배제, 협력 두 가지 동기화 기능을 제공.
- 상호 배제는 뮤텍스를 통해 제공하고, 협력은 조건변수를 사용하여 제공함.

### 2-1. 상호배제(Mutual Exclusion)
- JVM은 `synchronized 키워드`를 통해 상호 배제를 제공함.
- synchronized 키워드 내에 뮤텍스 동기화 기법이 들어있음.
    - synchronized 블록은 해당 객체의 모니터를 획득할 수 있음. 모니터를 획득한 스레드만 임계 영역에 접근 가능함.
    - synchronized 블록을 빠져 나오면 모니터 Lock이 해제됨. 대기 중이던 다른 스레드가 Lock을 얻음.
    - 이를 통해 상호배제가 보장됨.

### 3-2. 협력(Cooperation)
- 협력이 필요한 상황
  - Consumer가 소비해야 하는데 버퍼가 비어있는 경우
  - 이런 상황에 협력이 필요하다. 
  - Producer가 생산할 때까지 Consumer는 대기하고 Producer가 생성하면 Consumer를 깨운다.
- 특정 조건이 만족할 때까지 대기했다가 만족하면 대기 중이던 스레드를 깨운다. 이것이 협력이다.



- 협력엔 조건 변수가 필요하다. 자바의 모니터 안에 조건 변수가 있다.
- 조건 변수(Condition Variable)의 핵심 기능
  - wait & signal
  - 자바에선 wait() & notify()
  - wait() : 조건이 만족할 때까지 대기
  - notify() : 조건이 만족되면 대기 중이던 한 개의 스레드를 깨움.
  - notifyAll(): 조건이 만족되면 대기 중이던 모든 스레드를 깨움.

- 모니터는 여러 조건 변수를 가질 수 있지만 자바에선 오직 하나의 조건 변수를 가질 수 있다.
- 조건 변수를 통해 스레드 간 대기와 통지를 서로 조절하며, 이를 통해 경쟁 조건과 같은 문제를 방지할 수 있음.
  - 경쟁 조건? 여러 스레드가 하나의 임계영역에 동시에 접근해서 결과가 달라지는 현상.


### 3-3. 모니터 대기 세트 구조

- 자바의 모니터 내부에는 Entry Set, Wait Set이라는 대기 자료구조가 있다.

- `Entry Set`
  - 모니터의 Lock을 획득하려는 스레드가 대기하는 공간
  - Lock이 반납되면 Entry Set에서 대기 중이던 스레드가 락을 획득한다.

- `Wait Set`
  - 특정 조건이 만족할 때까지 대기하는 공간
  - Lock을 반납하고 Wait Set에 넣음.
  - 추후 특정 조건이 만족되면 다른 스레드에 의해 깨어나고, Entry Set으로 이동함.


### 3-4. 조건 변수 종류

- 조건 변수 종류도 여러 개 있지만 자바에서는 이미 조건 변수의 종류 중 하나를 채택하여 사용하고 있다.
- signal을 호출했을 때 누가 먼저 실행되되느냐의 차이.

- `Signal and Wait`
- `Signal and Continue`
  - 자바에서는 signal and continue를 사용

## 동기화 기법 4: SpinLock & Busy Waiting  
### 4.1 Spin Lock
- 대기하지 않고 스레드가 임계영역을 사용할 수 있을 때까지 계속 반복함.

- `test_and_set(&lock)` 함수가 스핀락으로 동작함.


### 4-2. Busy Waiting (바쁜 대기)
- 스핀락에서 스레드가 락을 획득하기 위해서 조건이 만족될 때까지 무한 반복하여 대기하는 것이 busy waiting 이다.
- 굉장히 비효율적.

### 4-3. 스핀락의 장단점
- 장점
  - 블로킹 대기X. 컨텍스트 스위칭 비용이 감소
  - 스핀락은 임계영역의 대기 시간이 짧을 때 유리하다.
- 단점
  - busy waiting으로 인한 CPU 리소스 낭비가 있다.
  - 스핀락은 공유 자원에 대한 경쟁이 많은 경우에는 비효율적이다.

- 싱글코어에서 스핀락을 사용하면 busy waiting으로 인해 성능이 저하될 수 있다. 따라서 스핀락은 멀티코어 환경에서 사용하는 것이 더 효율적이다.
- 스핀락은 멀티코어와 상관없이 `대기 시간이 긴 경우` 또는 `공유 자원 접근에 대한 경쟁이 많은 경우` 사용하면 안된다.
- 대부분의 경우, 스핀락보다는 뮤텍스, 세마포어 등의 블로킹 기반의 동기화 기법을 사용한다.
